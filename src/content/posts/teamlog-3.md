## Telnet
Telnet은 네트워크를 통해 다른 컴퓨터에 원격으로 접속할 수 있는 프로토콜이다
찾아보니 RFC 854에서 정의되어 있고 원격에 있는 터미널과 통신하기 위해 만들어졌다고 한다
보통 TCP 23번 포트를 사용한다
사용하는 방식은 
```plain text
컴퓨터
    ↓
Telnet
    ↓
서버
    ↓
로그인
    ↓
명령어 실행
```
이런 느낌이다
SSH로 서버에 접속하는 것과 비슷해 보이는데 큰 차이가 하나 있다
Telnet은 통신 내용을 암호화하지 않는다
그래서 네트워크에서 패킷을 확인할 수 있다면 Telnet으로 주고받는 내용도 그대로 노출될 수 있다
이러면 원격 서버 로그인에 사용하기에는 상당히 위험해 보인다
---
## telnet 설정(?)
Ubuntu에서 Telnet 서버를 사용하려면 다음과 같이 설치할 수 있다
```bash
sudo apt update
sudo apt install inetutils-telnetd
```
클라이언트에서는 **sudo apt install telnet** 로  Telnet을 설치하고
접속할 서버의 IP 주소를** ip addr**** **로** **확인한다
그리고** telnet 서버IP **로  접속할 수 있다
연결되면 로그인 화면이 나오고 계정으로 로그인하면 원격으로 명령어를 사용할 수 있다
직접 해보지는 않았지만 실습한다면 Ubuntu 서버 하나와 클라이언트 하나를 준비하고 이런 방식으로 접속하면 될 것 같다
---
## Telnet이 위험한 이유
앞서 말했듯이 Telnet은 통신을 암호화하지 않는다
예를 들어
```plain text
사용자
    ↓
아이디 / 비밀번호 / 명령어
    ↓
네트워크
    ↓
서버
```
이런 식으로 데이터가 이동한다
그런데 이 데이터가 암호화되어 있지 않기 때문에 중간에서 패킷을 볼 수 있다면 내용도 같이 확인할 수 있다
Wireshark 같은 프로그램으로 Telnet 패킷을 캡처하면 이런 특징을 확인하는 실습을 할 수 있다고 한다
전에 Wireshark로 HTTP 패킷을 분석했을 때도 패킷 내부에 여러 정보가 들어있는 것을 확인했는데 Telnet도 암호화가 되어 있지 않기 때문에 비슷하게 생각하면 될 것 같다
---
## Telnet과 SSH
그럼 SSH는 뭐가 다른지 찾아봤다
둘 다 원격 서버에 접속해서 명령어를 사용할 수 있다는 점은 비슷하다
```plain text
Telnet
사용자 → 평문 통신 → 서버

SSH
사용자 → 암호화 → 서버
```
가장 큰 차이는 역시 암호화였다
SSH는 통신 내용을 암호화하기 때문에 중간에서 패킷을 얻더라도 실제로 어떤 내용을 주고받았는지 알아보기 어렵다
그래서 지금은 서버에 원격으로 접속할 때 Telnet보다 SSH를 사용하는 것이다

# 세션
세션 하이재킹을 알아보기 전에 세션부터 알아봤다
HTTP는 Stateless 프로토콜이다
즉 이전에 어떤 요청을 했는지 기본적으로 기억하지 않는다
그런데 생각해보면 웹사이트에 한 번 로그인하면 페이지를 이동할 때마다 아이디와 비밀번호를 다시 입력하지 않는다
이때 세션을 이용할 수 있다
```plain text
로그인
    ↓
서버가 세션 생성
    ↓
세션 ID 발급
    ↓
브라우저에 저장
    ↓
요청할 때 세션 ID 전송
    ↓
서버가 로그인한 사용자인지 확인
```
쉽게 생각하면 세션 ID가 로그인했다는 것을 보여주는 값이라고 생각하면 될 것 같다
그래서 세션 ID가 다른 사람한테 넘어가면 문제가 생긴다
---
# 세션 하이재킹
세션 하이재킹은 정상 사용자가 사용하고 있는 세션 ID를 공격자가 탈취해서 그 사용자처럼 사용하는 공격이다
보통은 로그인을 하려면
```plain text
ID
Password
    ↓
로그인 성공
```
과정이 필요하다
그런데 이미 로그인된 사용자의 세션 ID를 가지고 있다면 이야기가 달라진다
```plain text
사용자 로그인
    ↓
세션 ID 발급
    ↓
세션 ID 탈취
    ↓
공격자가 같은 세션 ID 사용
    ↓
서버는 로그인된 사용자라고 판단
```
서버 입장에서는 정상적으로 발급한 세션 ID가 들어온 것이기 때문에 실제 사용자가 보낸 요청인지 공격자가 보낸 요청인지 구분하기 어렵다
결국 비밀번호를 몰라도 세션 ID를 가져가면 로그인 상태를 뺏을 수도 있다는 것이다
생각보다 세션 ID가 상당히 중요한 값이었다……
---
# 세션 ID 스니핑
스니핑은 전에 배웠던 것처럼 네트워크에서 지나가는 패킷을 캡처해서 내용을 확인하는 것이다
세션 ID 스니핑은 말 그대로 패킷을 확인해서 세션 ID를 얻는 방식이다
HTTP처럼 암호화되지 않은 통신이라면 쿠키에 들어있는 세션 정보가 네트워크를 통해 그대로 전달될 수 있다
```plain text
사용자
    ↓
HTTP 요청
Cookie: 세션 ID
    ↓
서버
```
이 중간에서 패킷을 얻을 수 있다면 세션 ID도 같이 노출될 수 있다
앞에서 Telnet도 암호화하지 않아서 위험하다고 했는데 결국 둘 다 **평문으로 중요한 정보를 보내면 위험하다**는 점은 비슷한 것 같다
---
# MITM
MITM은 Man In The Middle의 약자이고 중간자 공격이라고 한다
이름 그대로 사용자와 서버 사이에 공격자가 들어가는 방식이다
```plain text
사용자
    ↓
공격자
    ↓
서버
```
사용자는 그냥 서버와 통신하고 있다고 생각하지만 실제로는 중간에서 공격자가 통신을 보고 있는 것이다
만약 통신이 암호화되어 있지 않다면 여기서 세션 ID 같은 정보를 얻을 수도 있다
그래서 HTTP보다 HTTPS를 사용하는 것이 중요하다
HTTPS는 통신 구간을 암호화하기 때문에 중간에서 패킷을 가져가더라도 내용을 그대로 확인하기 어렵다
---
# XSS로 쿠키 탈취
세션 ID를 네트워크에서 가져오는 방법만 있는 것은 아니다
XSS를 이용해서 브라우저의 쿠키를 가져가는 방법도 있다
XSS는 웹사이트가 사용자의 입력값을 제대로 검사하지 않았을 때 공격자가 넣은 JavaScript가 다른 사람의 브라우저에서 실행되는 취약점이다
그리고 쿠키에 HttpOnly가 설정되어 있지 않다면 JavaScript에서 쿠키에 접근할 수 있다
document.cookie 를 실행하면 JavaScript에서 접근 가능한 쿠키가 나온다
만약 여기에 로그인에 사용되는 세션 ID가 들어있으면 공격자가 세션 ID를 얻을 수도 있다
그래서 XSS가 세션 하이재킹으로 이어질 수도 있는 것이다
---
# HttpOnly
그럼 HttpOnly가 뭔지도 알아봤다
쿠키에 HttpOnly를 설정하면 JavaScript에서 해당 쿠키를 읽을 수 없게 만든다
그래서 **document.cookie **를 사용해도 HttpOnly가 적용된 쿠키는 가져올 수 없다
XSS가 아예 없어지는 것은 아니지만 적어도 JavaScript를 이용해서 세션 쿠키를 바로 가져가는 것은 막을 수 있다
---
# Secure
Secure는 쿠키를 HTTPS 연결에서만 전송하도록 하는 속성이다
Secure가 없다면 HTTP 연결에서도 쿠키가 전달될 수 있지만 Secure가 설정되어 있으면 HTTPS에서만 전달된다
**HTTP**
- 쿠키 전송 X
**HTTPS**
- 쿠키 전송 O
세션 ID 같은 중요한 값을 암호화되지 않은 HTTP로 보내지 않게 하는 것이다
---
# SameSite
SameSite는 다른 사이트에서 요청이 들어왔을 때 쿠키가 전송되는 것을 제한하는 속성이다
처음에는 이름만 보고 무슨 뜻인지 잘 몰랐는데 말 그대로 같은 사이트에서 발생한 요청인지 확인하는 것과 관련된 설정이었다
다른 사이트에서 사용자의 브라우저를 이용해서 요청을 보내는 공격을 막는 데 사용할 수 있다
---
# 세션 픽세이션
세션 픽세이션은 세션 ID를 훔치는 방식이 조금 다르다
공격자가 이미 알고 있는 세션 ID를 피해자가 사용하게 만든다
그리고 피해자가 그 세션으로 로그인하면 공격자도 같은 세션 ID를 사용한다
```plain text
공격자가 세션 ID 생성
    ↓
피해자가 그 세션 ID 사용
    ↓
로그인
    ↓
공격자도 같은 세션 ID 사용
```
이런 식이다
그래서 사용자가 로그인했을 때 세션 ID를 새로 만들어주면 된다
로그인 전에 공격자가 알고 있던 세션 ID가 로그인 이후에는 쓸모가 없어지는 것이다
---
# 세션 ID 예측
세션 ID는 당연히 예측하기 어려워야 한다
만약
```python
10001
10002
10003
10004
```
이런 식으로 만들어진다면 다음 세션 ID가 뭔지 너무 쉽게 예상할 수 있다
공격자가 값을 계속 바꿔보면서 실제 사용 중인 세션을 찾을 수도 있다
그래서 세션 ID는 일정한 규칙으로 만들면 안 되고 충분히 무작위여야 한다
여기서 엔트로피라는 말이 나오는데 쉽게 생각하면 **얼마나 예측하기 어려운가** 정도로 생각하면 될 것 같다
---
# 세션 만료
세션 ID를 아무리 안전하게 관리해도 아예 탈취되지 않는다고 장담할 수는 없다
그래서 세션을 계속 사용할 수 있게 두는 것도 문제가 된다
예를 들어 로그인하고 몇 달이 지나도 같은 세션이 계속 살아있다면 공격자가 세션 ID를 얻었을 때 오랫동안 사용할 수 있다
그래서 일정 시간이 지나면 세션을 만료시키도록 한다
```python
로그인
    ↓
세션 생성
    ↓
일정 시간 사용
    ↓
세션 만료
    ↓
다시 로그인
```
이렇게 하면 세션 ID가 탈취되더라도 사용할 수 있는 시간을 줄일 수 있다
---
# 방어 기법
정리해보면 세션 ID를 지키는 방법은 여러 가지가 있었다
- HTTPS 사용
- HttpOnly 설정
- Secure 설정
- SameSite 설정
- 로그인 후 세션 ID 다시 발급
- 세션 만료 시간 설정
- 예측하기 어려운 세션 ID 사용
HTTPS는 네트워크에서 세션 정보를 쉽게 볼 수 없게 하고
HttpOnly는 JavaScript가 세션 쿠키를 읽는 것을 막고
Secure는 HTTPS에서만 쿠키를 보내게 한다
그리고 로그인할 때 세션 ID를 새로 만들면 세션 픽세이션을 막을 수 있고 세션의 사용 시간을 제한하면 탈취된 세션이 계속 사용되는 것도 줄일 수 있다
결국 세션 ID 하나를 보호하는 데도 생각보다 여러 설정이 필요했다
---
# 결론
Telnet부터 세션 하이재킹까지 알아봤는데 둘이 완전히 같은건 아니지만 공통점이  중요한 정보를 그냥 노출된 상태로 보내면 안 된다는 것 인것같다
Telnet은 통신 자체가 암호화되지 않아서 입력한 내용이 노출될 수 있고
웹에서는 세션 ID가 노출되면 로그인 상태 자체를 빼앗길 수 있다
처음에는 세션 ID가 그냥 서버에서 사용자를 구분하기 위한 랜덤한 값 정도라고 생각했는데 알아보니 비밀번호 못지않게 중요한 값이었다
세션 ID를 가지고 있으면 서버에서는 이미 로그인한 사용자라고 판단할 수 있기 때문이다
그래서 HTTPS나 쿠키의 여러 보안 속성을 이용해서 세션 ID가 노출되지 않도록 하고, 혹시 탈취되더라도 오래 사용하지 못하게 하는 방식으로 막는 것 같다
